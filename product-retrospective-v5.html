5.0

万能营销工作台 · 约 66 天

时间线与工作路径

3/4 启动年度规划三大场景之一，优先推进服装营销。
3 月上旬先框定模特图、编辑、视频、文案和详情页等能力范围。
3 月中下旬让 AI 直接输出 PRD，手改与 AI 修改反复往返，文档变得冗长且空泛。
3 月底—4/13多次内审；原型和交互不清。4/13 完成评审，较 3/20 计划延迟约半个月。
4 月—5/9Trae 原型不完整；UI 设计师补全；架构师沟通被业务输入输出不清拖慢。
5/9 上线核心能力基本覆盖预设范围，之后持续修复卡顿、中断、裂图和上下文问题。

个人卡点与结果

用户调研滞后

没有先确认真实输入、满意输出和中间过程。

过早考虑架构

业务边界未清就讨论多 Agent、skill 和提示词。

PRD 先行

关注文档和工具，推迟内审，团队无法体验方案。

原型能力不足

AI 原型一般，最终依赖 UI 手工兜底。

验收标准后置

缺少用户可接受的输入输出标准。

上线质量偏弱

错误率偏高，30 天留存率持续递减。

复盘判断：约 60 分版本。重做时应聚焦电商营销闭环，强化整套物料和视频能力，谨慎使用自由对话 + 画布。

5.1

设计生产工作台 · 设计到生产闭环

时间线与工作路径

年初规划 · 启动日期未记录更新老旧服装设计能力，并在闭环终点衔接工艺单。
前期调研参考 SaaS 功能，沟通日本客户和国内运营，确定设计、图案、面料、矢量和工艺单范围。
4/28 首次内审功能范围较清楚，但原型完成度一般，PRD 开始多轮返工。
5/20 二次内审 + UI 内审继续用手工原型和 UI 讨论细节，工具与步骤不稳定。
5/26 技术方案对齐业务范围相对明确后与工程组对齐可行性。
6/1 需求评审完成需求评审，进入后续开发与交付。
7/2 正式上线上线后，设计、图案等能力效果反馈较好；用户继续提出个性化需求，工艺单暴露审核与编辑问题。

个人卡点与结果

用户输入仍不够深

有客户和运营输入，但更多是一线转述。

四点没有前置

用户路径、边界、验收、技术方案形成较慢。

原型工具不稳定

AI 原型一般，最后大量手工绘制。

PRD 与原型返工

多轮对齐，UI 难以快速施工。

工艺单审核弱

用户没有意识到 AI 解析会强烈影响最终结果。

文字不可编辑

生图工艺单缺少文字分层和编辑能力。

复盘判断：效果整体较好，解决了旧能力和新场景问题。下一次先冻结四个前置点，用节点式交互和种子用户共创提高速度与验收质量。

5.2

灵感决策工作台 · 6/26—8/24

时间线与工作路径

6/26 产品讨论提出选品、企划、客户提案、款式裂变 4 个场景。
6—7 月 场景与数据取舍运营反复对逻辑；调研是否获取真实数据、供应商、格式和可行性。
7/7、7/21 讨论回顾筛选数据来源并验证质量，产品方案多轮重组。
约 1 周 种子用户共创补齐真实输入、过程、输出和验收标准，并制作 Demo。
8/10 对齐基于 UI 初稿，用 Codex/Coze 持续输出 HTML 可交互原型。
8/12 技术方案 · 8/17 UI 内审原型清晰后对齐技术，细化功能并推进 UI 终稿。
8/24 需求评审4 个预设场景收缩为 2 个上线场景。

个人卡点与结果

版本一开始过大

四场景并行，P0 筛选意识出现得太晚。

真实数据链路很长

从要不要做，到来源筛选、质量验证和应用。

验收后知后觉

场景确定后才发现输入、数据、过程、输出不清。

小版本打断主版本

无法衔接开发，中间插入多个小版本设计。

文档同步成本高

方案、重组版、主文档、PRD、原型、Agent 文档多次同步。

指标基线仍需前置

已列指标，但应在共创阶段开始采集。

复盘判断：后期比前两版顺畅，未再过早陷入复杂 Agent 架构。核心优化是第一阶段就做 P0 筛选、用户共创和数据可行性决策。

横向判断

问题从“业务没想清楚”逐步转为“范围、证据和基线如何治理”。

01 / 用户输入从内部推理到真实用户共创，但共创仍需前置
5.0

主要依靠年度规划和 SaaS 行为数据推理。快捷案例封装时才补问真实输入输出，架构讨论缺少业务依据。

5.1

更早沟通日本客户和国内运营，功能范围更清楚；直接客户交流不够深入，仍较依赖一线转述。

5.2

先与运营对齐四个场景，再用约一周开展种子用户共创，以真实企业任务和 Demo 补齐输入输出。

结论与下一步：进步是证据更真实；下一次应把共创放在范围确定之前，减少先设计再求证。

02 / 范围控制5.1 提早收敛，5.2 暴露多场景规模成本
5.0

结合已有能力、使用数据和研发可行性框定营销范围，但目标用户宽泛，缺少具体任务样例。

5.1

设计、图案、面料、矢量和工艺单范围较早确定，减少了方向争议，细节与验收仍需要补齐。

5.2

四个复杂场景同时展开，经过多轮讨论最终只上线两个；范围调整又增加方案修改时间。

结论与下一步：范围清楚不等于规模合适。立项时同时比较用户价值、变现价值、设计与开发成本、实现把握和紧迫度。

03 / 原型对齐从文字返工、手工补全，到 UI 初稿与 HTML 协同
5.0

先反复写 PRD，AI 原型不够完整；内审迟迟未开展，依赖 UI 补全并倒推交互说明。

5.1

范围更清楚，但工具和使用方法不稳定；AI 原型质量一般，最终大量手工绘制，PRD 多轮对齐。

5.2

先使用 UI 提供的核心页面样式，再持续生成可交互 HTML，内审后细化功能、衔接 UI 终稿，后段推进更快。

结论与下一步：提速来自“设计规范 + 可体验路径 + 及时评审”的组合，原型应先跑通关键行为，再追求细节完整。

04 / 验收标准三个版本都有后置问题，5.2 开始用共创补齐
5.0

未先明确用户可接受的输入输出，产品与架构难以对齐；负责人随后强调边界、场景和可验收标准。

5.1

已经建立验收标准，但没有与用户路径、功能边界、技术方案一起快速确定，造成后续补充。

5.2

场景确定后仍不清楚真实输入、需要什么数据和产物；通过企业用户调研与 Demo 推进标准和输入输出规范。

结论与下一步：标准逐步具体，但前置仍未完成。先用真实样例确定合格与不合格结果，再进入详细设计。

05 / 主要风险各版瓶颈不同，5.2 后段改善不代表质量风险消失
5.0

需求与 Agent 架构、实现反复校齐；上线后卡顿、裂图、上下文错误偏高，用户报告 30 天留存递减。

5.1

原型与 PRD 消耗时间；7 月 2 日上线后整体效果较好，工艺单的文字编辑和用户审核成为具体问题。

5.2

前期耗时集中在场景复杂度、数据选型及测试、补做共创和小版本插入；后期原型、UI、Agent 衔接明显改善。

结论与下一步：风险重心发生变化，不能据此推断旧风险已消失。分别跟踪决策周期、任务完成率、质量和留存；5.2 尚无量化结果支撑。

新的推进方案

固定六步，并为每一步设置清晰的进入条件。

01 发现种子用户共创真实任务、输入、失败案例
02 定义用户路径与边界P0、非目标、最终产物
03 验收输入输出样例可接受、不可接受、异常
04 验证交互原型内审先体验行为，再讨论文字
05 实现技术与 Agent状态机、工具、提示词
06 复盘指标回收激活、完成、耗时、留存
硬门槛：没有真实输入输出样例，不进入大规模 PRD；没有可交互原型，不进入 UI 施工；没有验收标准，不冻结技术方案。

Codex 分工与优先动作

让 Codex 负责整理、生成、同步和验证，把产品经理时间留给判断与取舍。

Codex 直接承担

以真实资料为输入，形成可评审产物，并根据人工反馈持续校正。

  1. 产品经理提供访谈、真实样例与已确认边界
  2. Codex整理事实与缺口，生成路径和验收草稿
  3. 产品经理 + 用户确认理解，纠正假设与遗漏
  4. Codex生成 HTML 原型，列出异常与待确认状态
  5. 团队 → Codex评审后同步 PRD、验收清单及变更记录

交付：原型、文档、验收项对应同一版决策。

产品经理必须判断

Codex 辅助比较方案，产品经理与用户、研发一起决定取舍。

  1. Codex归纳候选需求及现有证据，标明未知项
  2. 产品经理 + 用户判断任务价值，核对满意输出
  3. 研发 + UI评估可行性、设计成本和开发成本
  4. 产品经理结合变现价值和紧迫度确定 P0
  5. Codex → 产品经理记录范围与决策依据；变更时分析影响，再由人确认

出口：范围、验收和成本有依据，未决风险有负责人。

下一轮先做

先跑一个有用户价值、实现有把握的闭环，再决定是否扩展。

  1. 产品经理 + 种子用户选定典型任务，收集真实输入和期望输出
  2. Codex + 研发整理样例库，用同一任务验证数据与能力
  3. 用户 + 产品经理确认验收标准，筛选首批范围
  4. UI + Codex核心样式 → HTML 原型 → 可视化内审
  5. 团队 + Codex固定基线，上线后回收完成率、耗时和质量反馈

反馈回路：不达标时回到样例与边界，达标后再复制场景。
